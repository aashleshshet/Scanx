THE BEGINNER’S GUIDE

Your first API assessment.

Go from exploring a sample to running a scan on an API you own or have permission to test.

1. Explore without installing anything

  1. Open the dashboard. It starts with a synthetic sample: invented API responses, not a scan of a real service.
  2. Click a severity card, such as High, to filter findings. Click a finding’s title to see its evidence and suggested fix.
  3. Click Switch sample to compare vulnerable and protected examples.
  4. Choose JSON, Markdown, or HTML, then click Export report. JSON can be reopened with Import report.

The hosted website is a report explorer. It does not send test requests to your API. Imported reports stay in this browser tab; save an export before closing it.

2. Understand the three inputs

  • Base URL: your API’s starting address, for example https://your-api.example/v1. This example is a placeholder; replace it with your own.
  • API specification: an OpenAPI or Swagger JSON/YAML file describing routes, request parameters, and authentication. Ask your API developer for it, or export it from your API documentation.
  • Scenario file: known test values, such as two private order IDs belonging to different test users. Scanx needs these to distinguish unauthorized access from legitimate sharing.

Download the example specification and example scenarios to see the format. Replace their paths and IDs to match your API; they do not create an API server or user accounts.

3. Install the local web scanner

Install Python 3.11 or newer and Git first. Open Terminal (macOS/Linux) or PowerShell (Windows), then run:

git clone https://github.com/aashleshshet/Scanx.git
cd Scanx
python -m venv .venv

Activate the environment. On macOS/Linux:

source .venv/bin/activate

On Windows PowerShell:

.venv\Scripts\Activate.ps1

Install and start Scanx, replacing the target URL with your API root:

python -m pip install -e ".[web]"
scanx-web --target https://your-api.example/v1

Open http://127.0.0.1:8765 in your browser. Keep the terminal running. Press Ctrl+C there when you are finished. If python is unavailable, use python3 on macOS/Linux or py on Windows.

This runner serves one local operator. It is not a multi-user internet service; it binds to your own computer and only scans API roots you explicitly configure.

4. Run your first scan

  1. In the local dashboard, click New scan and select your configured target.
  2. Upload your specification. Add a scenario file when testing object authorization or routes that need specific parameter values.
  3. Select the authentication scheme. Enter credentials for two separate test users, A and B. For bearer authentication, paste the token itself, without the Bearer prefix.
  4. Start with the default authorization, authentication, headers, and CORS checks. Injection probes and the 50-request rate test are optional and create extra traffic. Enable them deliberately in your test environment.
  5. Click Run assessment. Watch progress, or cancel from the activity banner. Export the report when the scan completes.

For BOLA testing, create a private object owned by A and a different private object owned by B. Put those known IDs and expected response markers in the scenario file. Both users must be able to read their own object. A successful cross-user read is meaningful only when the object is intended to be private.

Credentials are used by the local runner and excluded from reports. Scenario environment variable names are ignored in web mode; enter the credentials in the form.

5. Read the results

  • Critical / High / Medium / Low: priority and potential impact. Start by reviewing confirmed High or Critical findings.
  • Confirmed: the test observed evidence matching its rule. Verify the API’s intended access policy before making a final judgment.
  • Needs review: a signal needs investigation; it is not proof of an exploitable vulnerability.
  • Coverage gaps: checks were skipped or inconclusive, often because a fixture or credential was missing.
  • Passed: that specific experiment did not find the tested behavior. A report with zero findings is not a guarantee of security.

Open each finding, review its evidence, apply the remediation, and rerun the same assessment to compare.

Common questions

Why does New scan show installation instructions?

You are using the hosted report explorer. Start the Python runner, then open its local address to run live scans.

Why is my target missing or rejected?

Restart the server with --target followed by the exact API root you need. Repeat that option for multiple roots. Redirects outside the configured scope are not followed.

Why was the object authorization check skipped?

Check that the scenario file has two distinct private object IDs, matching operation and parameter names, expected response markers, and credentials for different users. See the repository’s complete BOLA example for the exact structure.

Why can’t I reopen an HTML report?

Import accepts Scanx JSON reports. HTML and Markdown exports are for reading and sharing. Keep the JSON version if you want to explore findings again.

What if the local address does not open?

Keep the server terminal open and check it for errors. If port 8765 is occupied, start with --port 8766 and open http://127.0.0.1:8766.
